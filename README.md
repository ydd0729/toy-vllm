# Toy-VLLM

## Introduction

### The Baseline Project: `toy-vllm`

The basline is a refactored version of [tiny-vllm](https://github.com/jmaczan/tiny-vllm), an unfinished tutorial project with spaghetti code for building an LLM inference engine in C++ and CUDA for [Llama-3.2-1B-Instruct](https://huggingface.co/unsloth/Llama-3.2-1B-Instruct/tree/main). Compared with `tiny-vllm`, the baseline introduces the following improvements:

- **Refactoring:** Added a few structs and split the logic from the original `main.cpp` into multiple source files.
- **Tokenization:** Added a tokenizer based on [tokenizers-cpp](https://github.com/mlc-ai/tokenizers-cpp) to process user messages directly.
- **Command-line options:** Added two-command line options for reading user messages from a file and writing responses to a file. Usage: `toy-vllm.exe -f "input.txt" -o "output.txt"`
- **Bug fix:** `tiny-vllm` implements a kernel for Rotary Position Embedding (RoPE).[^2] The Hugging Face `transformers` version of LLaMA uses a GPT-NeoX-style RoPE layout, whereas Meta's original implementation uses an interleaved GPT-J-style layout.[^3] Therefore, when loading the Hugging Face `model.safetensors` weights, using a Meta-style RoPE kernel without matching the Hugging Face layout can cause incorrect outputs on order-sensitive prompts, such as "Sort these numbers: 3, 1, 2". To fix this, a new RoPE kernel was added. **Claude Fable 5 helped trace this known bug to the RoPE layout mismatch and implement the fix.**

#### Build Instructions

1. Clone the repo:

```powershell
git clone --recursive https://github.com/ydd0729/toy-vllm.git
```

2. Adjust `CMAKE_CUDA_ARCHITECTURES` in `CMakeLists.txt` to match your Nvidia GPU architecture.
3. Install [Hugging Face CLI](https://huggingface.co/docs/huggingface_hub/guides/cli).
4. Download [Llama-3.2-1B-Instruct](https://huggingface.co/unsloth/Llama-3.2-1B-Instruct/tree/main):

```powershell
hf download unsloth/Llama-3.2-1B-Instruct --local-dir models/Llama-3.2-1B-Instruct
```

5. Install Visual Studio 2026, CMake 4.3, Ninja 1.13.1, CUDA 13.2
6. Use CMake to configure & build.

### Performance Measurement

The LLM inference can be viewed as two phases: prefill and decode. In the prefill phase, all input tokens are passed through the model to fill the KV cache and produce the first output token. In the decode phase, each newly generated token is fed back to the model to generate the next token, until an EOS token is met.

Timestamps are recorded at the boundaries of the inference pipeline. In general, 4 phases are measured:

1. Tokenization
2. Prefill
3. Decode
4. Detokenization

The `test/input.txt` contains 256 user messages, generated by GPT-5.5, that are used as input for performance measurement. Execution time is measured as the average over 5 runs using a release build.

### Profiling

#### Profiling Build Configuration

`toy-vllm` is a CMake project. To profile the program while keeping performance as close as possible to a release build, `CMAKE_BUILD_TYPE` is set to `RelWithDebInfo`, meaning that this build enables compiler optimizations while preserving debug Information, so that the profiling tools can map performance measurements back to the source code and API calls.

#### Profiling Tools

#### [AMD uProf](https://www.amd.com/en/developer/uprof.html)

Time-based profiling in this report is performed with AMD uProf by sampling the program at fixed intervals. At each sample, it records information such as the current call stack and instruction pointer. The number of samples attributed to each function is then used to estimate how much CPU time that function consumes.

##### [NVIDIA Nsight Systems](https://developer.nvidia.com/nsight-systems)

NVIDIA Nsight Systems is a powerful profiling tool for system-wide performance analysis. It records CPU and GPU activity, CUDA API calls, kernel executions, and thread activity during profiling. It provides multiple views for visualizing the results, including a timeline view that shows different types of activity on separate timelines.

##### Windows Task Manager

Windows Task Manager shows basic hardware usage. CUDA programs require manual resource management. With Windows Task Manager, it is easy to identify whether memory or compute resources are still available. If so, some relevent parameters could be tuned in the program to better utilize the resources. Although the best settings could often be inferred from the hardware specifications, this is still a simple and useful way to verify resource utilization. In addition, no special build configuration is needed.

### V1: Increasing `KV_CACHE_SIZE_BYTES` and `BATCH_SIZE`

This inference engine is designed to process multiple prompts in parallel, with the degree of parallelism controlled by `BATCH_SIZE`. `KV_CACHE_SIZE_BYTES` controls the size of KV cache. In the baseline, `BATCH_SIZE` is set to 2 and `KV_CACHE_SIZE_BYTES` is set to 2 GiB. Windows Task Manager shows that only half of the GPU memory is used:

![634](Pasted%20image%2020260708170541.png)

The GPU has 12 GB of dedicated memory, and less than 1GB is used by Windows and other background GPU usage. The model weights take up about 2.5 GB. Therefore, the maximum safe size of the KV cache is roughly 8.5 GiB.

`toy-vllm` implements a **halfway** version of paged attention,[^4] whose concept is derived from the virtual memory and paging in operating systems. It stores the KV vectors for a fixed number pf tokens in each block. Physical blocks do not need to be contiguous in memory. A block table maps logical blocks to physical blocks, giving the illusion that the logical blocks are contigious. This helps allocate memory more efficiently when the number of token to be generated is not known in advance during the decode phase. The missing half is the logic for handling the case where there are no free blocks. So, the current implementation doesn't increase throughput. For now,  to ensure that the inference engine works properly, this case must not occur. 

Other relevent configurations include:

| Constant                                                               | Meaning                                                                            |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `MAX_SEQ_LEN = 2048;`                                                  | The maximum number of all tokens in a sequence (input tokens and generated tokens) |
| `BLOCK_SIZE = 16;`                                                     | The number of  one token's KV cache in a block                                     |
| `MAX_BLOCKS_PER_SEQ = MAX_SEQ_LEN / BLOCK_SIZE; // 128`                | The maximum number of blocks required by a sequence                                |
| `KV_DIM = 512;`                                                        | The dimension for K and V matrix.                                                  |
| `BLOCK_BYTES = BLOCK_SIZE * KV_DIM * sizeof(nv_bfloat16) * 2 // 32768` | The size of a block.                                                               |
| `NUM_BLOCKS = KV_CACHE_SIZE_BYTES / BLOCK_BYTES;`                      | The maximum number of blocks.                                                      |
| `N_LAYERS = 16;`                                                       | The number of layers of the model.                                                 |

To make sure the number of blocks is enough, the maximum `BATCH_SIZE` should be:

$$
\text{BATCH\_SIZE}=\frac{\text{NUM\_BLOCKS}}{\text{MAX\_BLOCKS\_PER\_SEQ}\times \text{N\_LAYERS}}
$$

When `KV_CACHE_SIZE_BYTES` is set to 8.5 GiB, the maximum `BATCH_SIZE` is 136.

Now the engine uses almost all of the dedicated GPU memory:

![657](Pasted%20image%2020260708190431.png)

### V2: Moving `ArgMax` to the GPU

NVIDIA Nsight Systems shows there are many `cudaMemcpy` calls in V1:

![798](Pasted%20image%2020260709165840.png)

Some of these calls are data transfers between the CPU and GPU. Performance can be improved by eliminating unnecessary memory copy operations.

In `prefill`, the input tokens are passed through the model, and finally hidden states are projected back to logits. In `decode`, logits are produced at each step. Under greedy decoding, the token with the largest logit is selected as the next token to be fed back into the model.

This `argmax` logic is implemented on the CPU in both `prefill` and `decode`. First, the logits are copied back to CPU memory. Then`token_idx` is iterated over `VOCAB_SIZE`, which is 128256 for Llama 3.2 1B.

Assume that the number of input tokens is $30$, which is a relatively short prompt. Then the size of the memory copy in `prefill` is:

$$
30\times 128256 \times 2 = 7,695,360\ \text{B}= 7.34 \text{MiB}
$$

In `decode`, the copy size is also multiplied by the number of active slots, which can be as large as `BATCH_SIZE`.

```cpp
cudaMemcpy(ctx.logits_cpu.data(), 
	       ctx.logits,
           sizeof(__nv_bfloat16) * ctx.input_token_len * VOCAB_SIZE,                          cudaMemcpyDeviceToHost);

int last_token_offset = (ctx.input_token_len - 1) * VOCAB_SIZE;
float max_logit = (float) ctx.logits_cpu[last_token_offset];
int max_token_idx = 0;

for (int token_idx = 0; token_idx < VOCAB_SIZE; ++token_idx)
{
	if ((float) ctx.logits_cpu[token_idx + last_token_offset] > max_logit)
	{
		max_logit = ctx.logits_cpu[token_idx + last_token_offset];
		max_token_idx = token_idx;
	}
}
```

This is also quite a heavy loop because `VOCAB_SIZE` is large. The overhead is especially significant in `decode`, where the loop has to be executed once for each active slot in each step. 

AMD uProf shows that this part of code is the most significant hotspot both in `prefill` and `decode`:

![794](Pasted%20image%2020260709171134.png)

![794](Pasted%20image%2020260709171112.png)

In V2, `argmax` is implemented as a CUDA kernel on the GPU. The host no longer needs to copy the entire logits back to CPU memory. Instead, it only copies back the selected token index for each active slot.

### V3: Completing PagedAttention

In V1 `BATCH_SIZE` is set to its maximum possible value, 136, because the current implementation has no mechanism for handling the case where no free blocks are available. Profiling V2 with NVIDIA Nsight Systems shows that 53.3% of GPU time is spent in `PagedAttentionKernel`. It is merely overhead because of paging if it does not improve throughput.

![292](Pasted%20image%2020260709200717.png)

When there are no free blocks, some blocks need to be freed. The easiest way to do this is to discard some slots and free all the blocks allocated to them. The corresponding prompts are then added back to the prompt queue. A simple strategy is to choose the slot with the fewest generated tokens. This is not a fair strategy, but it is sufficient for further increasing `BATCH_SIZE`.

In V3, `BATCH_SIZE` is set to $136\times 4=544$ , which is four times the worst-case batch size the KV cache can hold. In practice, however, discarding should not occur very often as long as `BATCH_SIZE` is reasonable, because most token sequences are much shorter than `MAX_SEQ_LEN`. In fact, no discarding occurs in the test.

### V4: Copying `block_table` Only Once per Decode Step

Profiling V3 with NVIDIA Nsight Systems shows that there are a large number of `cudaMemcpy` calls and 66.3% of the CUDA API time is spent in waiting `cudaMemcpy`:

![Pasted image 20260710141919](Pasted%20image%2020260710141919.png)

the `block_table` is responsible for mapping logical block indices to physical block indices. The size is `BATCH_SIZE` × `N_LAYERS` × `MAX_BLOCKS_PER_SEQ` × `sizeof(int)` = 4456448 B = 4.25 MiB . Although this is not a large amount of memory, it is copied too many times in `decode`. The problem with so many small `cudaMemcpy` calls is that synchronous memory copies can introduce significant synchronization overhead.[^5] In the same stream, a `cudaMemcpy` is ordered after the kernels submitted before it, so the host may have to wait until the preceding GPU work has completed before the copy can finish.

In `decode`, `block_table` is copied to GPU in each step of the `for` loop that iterates over the 16 layers of the model. This is because in each layer, a new physical block may be allocated. However, whether a physical block needs to be allocated depends only on the current sequence length of each slot. Therefore, another `for` loop can be added before iterating over the layers to allocated all the physical blocks required by all sequences in the current `decode` step.

After decoding, `decode` recycle blocks from the slots that have finished generating. Another memory copy is then called that is completely unnecessary, because no kernels are invoked afterwards. The `block_table` will be synchronized to the GPU at the beginning of the next `decode` call.

 In V4, the number of  `cudaMemcpy` calls is further reduced by optimizing `decode` so that `block_table` is copied only once per decode step.

## Conclusion

The final version achieved a 5.37× speedup over the baseline. Since `tiny-vllm` was already a GPU-accelerated LLM inference engine, the optimizations focused on making better use of hardware resources and reducing memory copies between the host and the device. According to the profiling result, more than 85% of the GPU time is spent running the PagedAttention kernel and the cuBLAS kernel (`Kernel2`). Therefore, the potential performance gains from optimizing other kernels are limited. An attempt to optimize `pagedAttentionKernel` failed possibly because the seemingly optimized version increased warp stalls and made it harder for the GPU to hide memory latency.
